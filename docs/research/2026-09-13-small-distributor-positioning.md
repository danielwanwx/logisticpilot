# LogisticPilot：从小型分销商的一件难事切入

2026-09-13 UTC / 2026-09-12 Pacific。承接 [ROI 研究](2026-09-13-distributor-agent-roi-research.md)。用户已明确小企业优先、参赛范围与 UI 验收方式；下述具体产品方案是据此形成的建议，不代表新增能力已经实现。

## 定位建议

**LogisticPilot 帮助没有专职供应链分析师的小型零部件分销团队，查清到货异常，选出有依据的履约方案，并核验处理结果。**

用户买到的应是一项可完成的工作：货少了、质检有问题、客户又在催时，有人替他把单据和约束查清，把可行选择和费用摆出来，批准后把结果办进现有系统。经济主张来自少做重复工作、减少错误处置、减少可证明的额外费用；不能把所有可能价值都提前算成收益。

## “面向小企业”需要比“便宜版 Oracle”更具体

低成本有吸引力，但不是市场空白。当前美国公开价格页显示 Microsoft Dynamics 365 SCM 为每用户每月 $210、按年支付；Business Central Essentials 为 $80、Premium 为 $110，且已有销售订单、应付 Agent 的相邻能力，相关用量另计。它们不是相同功能包，也不是实施总成本。[1][2]

ERPNext 本身开源免费，托管、实施和支持另有成本；Odoo 也公开提供免费单应用及付费方案。因此不能声称“小企业没有 ERP 或 Agent 可用”，不能从大套件订阅价格推导我们的客户一定愿意购买。[3][4] Oracle 的具体总拥有成本本研究没有同口径报价，不编造价格差。

我们的竞争假设应是：**比自己翻 ERP、邮件和表格更省事，围绕一个异常直接完成工作，接入和学习成本足够低。** 是否便宜需要核对模型、托管、连接器、人工配置和维护成本；当前仓库运行仍依赖配置和凭据，不能宣传已经零配置安装。

## 首批用户画像：按工作方式筛选

以下是待真实用户验证的画像，不是已验证市场规模或客户名单。

| 维度 | 优先对象 | 为什么 |
| --- | --- | --- |
| 业务 | 零部件批发／分销，有批次、收货与客户订单 | 与现有真实 ERP 链最接近 |
| 人员 | 采购、仓库、客服由少数人兼任，没有专职分析师 | 证据查找和跨角色交接的负担集中在具体人身上 |
| 系统 | 已用 ERPNext，供应商信息仍部分在邮件或附件 | 可以从现有系统加一项工作能力，避免先卖一次 ERP 迁移 |
| 问题 | 经常遇到短装、到货质检、承诺变更；存在客户交期或拆单限制 | 足够频繁且有判断，才可能覆盖工具成本 |
| 决策人 | 老板或运营负责人，可以判断一次错误／加急的实际成本 | 收益和批准责任容易对应 |

首版不以“任何 Excel 小店”“所有 ERP 通用”“高度受监管制造工厂”为目标。可以展示未来适配文件的方向，但未实现的输入方式不进入功能承诺。小客户的数据可能更散、更不规范，接入成本必须验证，不能假设企业越小实施越简单。

## 演示只围绕一个人、一个异常、一个决定

建议角色是兼任采购和客户交付协调的小团队运营人员。当天一批零件发生短装与质检异常，两张客户订单在等货。他需要回答：“什么能发、发给谁、怎样处理更合算、剩下的问题由谁跟进？”

| 演示阶段 | 用户看到什么 | Agent 必须实际做什么 | 可证明的结果 |
| --- | --- | --- | --- |
| 接到异常 | 一条明确待办，有客户承诺和影响范围 | 读取当前订单、收货与质量记录，发现缺失或冲突 | 定位到同一批次、原生单据与观察时点 |
| 查清依据 | 简明事实及可展开来源 | 取回适用条款，区分合格、隔离、缺货；明确未知项 | 证据支持的可用数量与约束 |
| 给出选择 | 等待／部分发货／加急中的少量可行方案 | 解释适用条件，按需查找费用证据；确定性逻辑算数 | 有依据的成本比较；数据不足时不能假装最优 |
| 批准办理 | 用户批准准确方案 | 在批准范围内执行现有支持动作并读取原系统结果 | 实际 DN／Shipment 等单据与状态 |
| 看清结果 | 完成了什么、剩下什么、花了多少工作 | 归纳已执行事实与后续责任 | 发出数量、订单行价值、处理时间、费用状态各自标明口径 |

这里的主动性是 Agent 根据任务缺口选择下一次调查和可行处置，不是多显示几个工具图标。让同一流程遇到不同合同或运费时改变建议，比始终复述预编译计划更能展示推理贡献。多 Agent 只在质量与商业调查分工确实改善结果时保留，不以数量作为卖点。

现有 PO20 是已完成的保留证据案例，A20 的发货早于 B18 的到货失败。若采用上述新因果场景，需要另建明确标记的演示案例并真实走通；不能重新包装旧时间线。合成交易背景可以使用，必须标注；真实调用与原系统写入不能替换为 mock。

## 小而精的范围

**首版证明四件事：** 查得清楚；方案有理由；批准后真办成；结果可核验。收益先看实际人工处理负担和可证明的费用差，订单金额只作为业务规模。

供应商追偿很有潜力，但只有具备适用合同、费用凭证及贷项／结算链时才展示“已追回”。否则它可以是清楚标记的追偿证据草稿，不能冒充经济结案。趋势监测作为后续有价值的调查信号，不能为了显得先进而堆入首屏，更不从单案推导生产良率。

64 项指标目录用于选痛点和判断数据缺口，不全部实施。优先检验这些问题：异常是否经常发生？运营人员实际花多少活跃时间？哪些费用确实发生？同样工作用 ERP 报表或简单规则能否更便宜地完成？用户是否愿意持续用，而非只觉得 demo 有趣？

## 验收纪律

- 不新增 UI 单元测试。最终视觉、布局与交互由用户 review。
- Agent 负责必要的真实流程检查：按钮是否调用正确后端、数据是否真、批准是否执行目标动作、原系统是否读回结果。
- 只对变化的金额计算、库存状态与批准边界做必要的聚焦检查；不为参赛扩展全量生产可靠性、无关边界或重复回归。
- 真实联通、诚实标签和每个里程碑 commit/push 保留；它们直接支撑 demo 的可信度。
