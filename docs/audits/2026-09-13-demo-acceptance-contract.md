# LogisticPilot demo acceptance contract

Date: September 13, 2026 UTC / September 12 Pacific. Status: **review contract, not a passed acceptance report**. The user has not yet agreed the revised demo scenario. This document does not select that scenario, authorize new external records, or require a new framework.

The minimum credible deliverable is one understandable business decision, a working approval-to-result path, inspectable evidence, and free judging access to the product represented in the film. Every accepted claim must name its case, software version, mode, and verification date. Historical PO20 execution, current retained conversation, and a proposed new demonstration remain separate evidence.

## Required submission gates and the recommended competitive bar

The official requirements below come from the [September 13 rules review](../research/2026-09-13-multiple-submissions-rules.md), which checked official sources on September 12. This document did not browse or obtain a new organizer determination.

| Item | Official requirement | Reviewer acceptance recommendation |
| --- | --- | --- |
| Working agent | Meaningful Strands use; an agent handling a real task end to end rather than only discussing it. | Show the actual model invocation and the evidence-dependent contribution that matters to the operator. Do not treat a precomputed plan ID as proof of independent allocation reasoning. |
| Judge access | Free access through a website, functioning demo, or test build until judging ends. A live-demo URL is optional as a field. | A fresh judge session can perform the central workflow from the film without private developer files, the entrant operating the machine, or judge-funded model usage. Clearly identify any difference in external effects. This equivalence standard is a reviewer recommendation, not additional quoted rules. |
| Video | Public YouTube/Vimeo video, no longer than five minutes, showing the working project, problem, user, and importance; English or the required translations. | Verify public playback while signed out and inspect the exported film for readable evidence, honest chronology, and a visible consequence. A local export is not public-video acceptance. |
| Repository/package | Public repository with necessary source, assets, setup instructions, README, and MIT or Apache licensing visible as required. Architecture diagram and AWS Builder ID are required submission material. | Test the documented entry from a clean environment. The README, diagram, film, and judge route must identify the same product path and model transport. |
| Evaluation/hosting | An evaluation suite and AgentCore are not mandatory. | Use only the smallest relevant evidence comparison; retain the simpler implementation if no benefit is demonstrated. Do not add Graph, AgentCore, or an eval badge solely to increase feature count. |

The five criteria are equally weighted: Technical Implementation, Design, Potential Impact, Creativity & Originality, and Presentation; Technical Implementation is the first tiebreaker. Deadline: September 14 at 17:00 Pacific. Passing this contract would support a bounded submission, not predict an award.

## Cross-scenario acceptance record

Use one compact evidence record for the agreed central path. Record source commit and running build identity, entry URL, case and native document identities, model/configuration, source mode/as-of time, observed input, expected result, actual result, and links to the supporting capture/readback. Do not reuse a test count from a different build as new acceptance.

| Boundary | Smallest evidence that passes | Evidence that does not pass |
| --- | --- | --- |
| Current interface and controls | The reviewer operates each control exposed along the agreed path in the running build and checks its stated result. For a read control: content, case, and freshness are correct. For proposal/approval: the exact proposed fields and resulting state are checked. Disabled/unavailable controls give a truthful reason. A focused automated check covers a changed coupled behavior where useful. | A handler exists, a button is visible, an unrelated screenshot looks polished, or an old browser audit passed. The coordinator's control inventory supplies the coverage list; this review does not duplicate that audit. |
| Business decision | The displayed evidence supports the proposed action, quantities, lot scope, and contract terms; uncertainty is explicit. One counterexample changes the relevant conclusion instead of rephrasing it. | A persuasive answer that contradicts stock state, silently ignores another eligible customer, or repeats an application-supplied answer. |
| Approval and execution | The visible approval binds the current case/proposal/revision and exact effect. A successful action is followed by independent native readback of that effect. Rejection or stale/changed evidence cannot authorize it. A local repeat/reload check is used if persistence or replay is claimed. | Approval implied from conversation, a draft pick used as dispatch proof, a success toast without readback, or historical synthetic operator attribution presented as authenticated enterprise identity. |
| Result and explanation | The after-state and explanation agree with the native records and with what actually happened during this run. The user can open the evidence supporting the result. | A dashboard total alone, a proposed action counted as completed, or synthetic carrier confirmation counted as physical receipt. |
| Failure and recovery | One relevant negative check demonstrates a truthful unavailable/needs-evidence state without invented advice or false execution success. Repeat only checks affected by subsequent changes or failures. | Provider fallback concealed from the viewer, stale success left visible as current, or tests broadened indefinitely without a concrete defect. |

These checks cover the selected path and its material negative boundary. They do not certify every legacy tab, integration, or rare edge case. If a prominently presented control is outside that scope, its status must be clear; its mere presence cannot become a public claim that it works.

## Timing, source mode, and claim boundaries

| Mode | What may be claimed | Required evidence/label |
| --- | --- | --- |
| Historical execution | Named records were created by the historical demo and supported its recorded result. | Original case/date and actual retained proof. A later fresh ERP read may corroborate the end state but does not recapture the earlier click or its cause. |
| Retained review with a real model | A new real Strands/Bedrock answer interprets a dated evidence snapshot. | `RETAINED_AS_OF` and its date remain visible; sources and answers do not imply fresh ERP/SaaS retrieval or new writes. Request/model evidence distinguishes real inference from replay. |
| Fresh read | The specified source was queried during the current check and returned the stated facts. | Read time, source/case/document identity, source response status, and the actual returned fields. Fresh ERP does not make retained Slack/Jira/Airtable entries fresh. |
| Fresh execution | An authorized action in the current run created/changed the named native records. | Exact proposal, approval, execution receipt, and independent readback; preserve chronology across cuts. |
| Simulation/replay | Synthetic observations or local simulated effects exercise the disclosed demo workflow. | Label input provenance and simulated versus native effects. Replaying a stored model response is not a new agent invocation. |

The current runbook's retained setting disables new operations. Conversely, live projection is **not** a server-wide read-only setting; it can expose operation controls. Access acceptance must check the mode actually served, not assume that a read-only audit procedure configures read-only authority.

For PO20, A20 was dispatched before LOT-B's failed sample. An edited film cannot reverse this chronology or say that the later hold caused that earlier dispatch. Any later retest must be identified as operator-supplied evidence with an explicit time transition, not an instantaneous physical repair by the agent. A failed two-unit sample supports the recorded conservative lot hold; it does not prove all 18 units defective. Dispatch, physical delivery, order amounts, invoicing, and payment remain distinct.

## A valid, minimal agent-value comparison

Current evidence does not establish incremental agent value. The [development audit](2026-09-12-receiving-evals-development.md) reports failed Nova and Opus development workflows and no completed held-out decision. The older 8-case/15-conversation results belong to other paths. The [source review](../research/2026-09-12-strands-multiagent-evals-evidence.md) finds that current conversation tools return already-materialized payloads also included in the prompt, while the allocation selector may accept the one supplied plan ID or defer. A real tool call proves invocation; it does not prove that retrieval was necessary or external.

The coordinator's current source inspection further confirms that whole-lot PASS for A prepares the A20 plan before LOT-B failure. It also corrects an earlier scenario-review shorthand: changing A to disallow partial delivery makes **B15 eligible, leaving 5 unallocated**, under the provisioned B contract. It does not mean no customer can ship. These are deterministic contract regressions, not proof of model superiority.

Before testing, name the agent-owned question. It must require something not already supplied as the expected answer: for example, interpreting the scope or applicability of source evidence. This contract does not choose the new feature or scenario. Arithmetic and authority gates should remain deterministic.

Minimum recommended comparison for an approved narrow change:

1. Freeze the retained baseline, proposed single-agent version, source records, independent expected conclusions, question wording, allowed tools, model/configuration, common resource cap, and stop rule. Preserve baseline strengths; do not deliberately withhold facts only from the baseline. The baseline may properly defer where operator interpretation is required.
2. Use a small untouched set covering the target interpretation, a changed material fact/term, missing authoritative evidence, and a simple control where extra reasoning should add no value. A four-case pilot with two model repetitions is a feasible narrow acceptance sample, not a replacement score for the existing 32-run Graph protocol or an estimate of production accuracy. Author exact cases only after the scenario and agent responsibility are agreed.
3. If claiming agent retrieval, put source facts behind tools whose parameters affect retrieval; do not also embed the complete answer-bearing snapshot. If claiming reasoning over a snapshot, say so and test that directly. Exclude answer keys, expected verdicts, precompiled feasible plans, and retained model answers from the candidate input when those would solve the tested question.
4. Score exact conclusions and relevant missing-evidence states, citation scope, unsupported claims, completion/timeout/error, and authority violations. Record all starts, raw outcome classification, model usage, latency, and cost. A blank defer is not automatically correct. Blinded semantic review supplements deterministic assertions; another model's judgment is not ERP truth.
5. A narrow improvement claim requires a repeatable useful correction on the frozen target cases, no material regression on controls, zero critical business/authority errors, and a response time suitable for the film. If outcomes are unchanged, report explanation/retrieval behavior actually demonstrated and leave incremental decision value unproven. Promote to the product only after the actual interface and relevant end-to-end effect pass separately.

No paid calls are authorized by this document. Changing the target after seeing the held-out answers creates a new candidate and requires new untouched evidence; retain the earlier failures.

## Two feasible judge-access routes and their current gaps

Neither route is accepted today. No hosting, IAM, credential-sharing, security, or external-service change was performed or authorized by this review. These are delivery choices, not instructions to expose the current local server.

| Route | What the judge can test | Concrete gap before acceptance | Honest claim limit |
| --- | --- | --- | --- |
| **1. Entrant-hosted isolated demo** using the current `/operations` application and entrant-funded real agent access | Open the provided route, inspect source evidence, ask new questions, and exercise the agreed proposal/approval/result path in an explicitly scoped demo case. External ERP effects may be enabled only within that route's separately approved scope. | The reviewed entry is bound to `127.0.0.1:8930`, with private configuration/journal and provider access. No public judge route or availability through judging is verified. A supplied route must pass an independent fresh-session test without developer login state or local files, disclose retained versus executable mode, and provide a usable fresh demo/reset path if repeated execution is promised. | A hosted retained review can demonstrate real current Q&A and inspect historical execution, but does not let the judge execute that historical case anew. Do not call it equivalent to an interactive fresh execution path unless that path is actually available. |
| **2. Downloadable local `/operations` test build** with purpose-built public synthetic case data, a local simulated ERP adapter, and optional/native integration instructions kept separate | Start from the documented clean package, perform the same visible business workflow with simulated native effects, and inspect its evidence. A real Strands path must also be available at no judge cost if the package is represented as equivalent testing of the agent. | Current `make bootstrap` installs dependencies but does not supply the private case JSON/journal. `make case-console` and `make judge-demo` exercise a different historical entry. No self-contained current operations package or funded agent-access mechanism is verified. Real-agent testing would need an entrant-provided existing service/access mechanism or another verified cost-free provision; requiring the judge's billed AWS account does not close that gap. Verify the package without the entrant's environment or credentials. | Local ERP simulation demonstrates workflow behavior, not fresh external ERP effects. Replay/scripted answers may support offline inspection only and must be labeled; they do not establish real-agent equivalence. If the real agent cannot be tested freely, retain that explicit limitation rather than describe an offline replay as the complete current product. |

Route 1 is the stronger match for a film centered on real Strands reasoning plus native ERP effects, if the needed existing access can be made available within authorized scope. Route 2 is a credible reproducibility route when the simulated boundary and agent-access arrangement are honest. A free video or downloadable evidence archive alone is not evidence that a functioning test build exists. Whether a materially limited build satisfies the organizers is not determined by this reviewer.

Acceptance closes with one actual fresh-session walkthrough of the selected access route, not with a plan to provide access. Record which film actions the judge can reproduce, which effects are simulated, which evidence is retained, and any feature deliberately unavailable there. Keep unsupported outcomes out of the submission until the matching evidence exists.
